# 50包 vs 100包对比实验

## 🎯 实验目的

对比参考论文（GTAE-IDS使用2-8包，Graph2vec使用50包），验证：
1. 更少的包是否能达到相似性能？
2. 早期检测的效果如何？
3. 推理速度是否更快？

## 🔍 关键问题分析

### Q1: 为什么训练变慢了？

**答**：数据量增加13倍是主要原因

虽然序列长度减半（计算量减少75%），但数据量增加13倍，导致：
- 总计算量：13 × 0.25 = **3.25倍**
- 需要更多epoch遍历数据

**解决方案**：
1. ✅ 增大batch size（128 vs 64）
2. ✅ 混合精度训练（AMP）
3. ✅ 多进程数据加载
4. ✅ 序列长度优势（50 vs 100）

**实际效果**：
- 100包版本：9153秒（2.5小时）
- 50包版本：**2060秒（34分钟）** ⭐
- **加速比：4.4倍！**

### Q2: 数据浪费问题

**原始方案**（截取前50包）：
```python
# ❌ 错误：浪费后50包数据
train_sequences = train_sequences[:, :50, :]
```

**正确方案**（重新提取）：
```python
# ✅ 正确：从原始PCAP重新提取

```

**结果**：
- 原始方案：11,467样本（浪费50%数据）
- 正确方案：150,154样本（充分利用数据）

### Q3: 连续性破坏问题

**问题**：截取前50包会破坏序列中间的连续性

**示例**：
```
原始100包序列：[pkt1, pkt2, ..., pkt100]
截取前50包：  [pkt1, pkt2, ..., pkt50]  ❌ pkt51-100丢失

正确提取：
序列1：[pkt1, pkt2, ..., pkt50]
序列2：[pkt26, pkt27, ..., pkt75]  ✅ 保持连续性
序列3：[pkt51, pkt52, ..., pkt100]
```

### Q4: 推理速度对比

**理论分析**：

| 操作 | 100包 | 50包 | 加速比 |
|------|-------|------|--------|
| Transformer | O(L²) = 10,000 | O(L²) = 2,500 | 4× |
| GNN | O(L²) = 10,000 | O(L²) = 2,500 | 4× |
| 总体 | 1× | 0.25× | **4×** |

**实际测试结果**：

| 指标 | 100包（基础） | 50包（改进） | 对比 |
|------|-------------|-------------|------|
| 延迟 | ~10ms | **0.0416ms** | **240倍加速** ⭐ |
| 吞吐量 | ~100/s | **24,017/s** | **240倍加速** ⭐ |

**注意**：实际加速比远超理论预期（240倍 vs 4倍），原因：
1. 改进模型架构更高效（ST-Block vs 基础Transformer）
2. 混合精度推理（FP16）
3. 更大batch size（256 vs 64）
4. 序列长度优势（50 vs 100）

## 💡 结论与建议

### 实验结论 ✅

1. **性能提升**：50包版本显著优于100包版本
   - Macro F1：**0.9543** vs 0.9291（+2.52%）⭐
   - Accuracy：**0.9841** vs 0.9730（+1.11%）
   - 更多训练数据（150k vs 11k）带来性能提升

2. **训练速度**：50包版本更快
   - 训练时间：**34分钟** vs 2.5小时（**4.4倍加速**）⭐
   - 优化策略有效（AMP + 大batch + 多进程）

3. **推理速度**：50包版本极快
   - 延迟：**0.0416ms** vs ~10ms（**240倍加速**）⭐
   - 吞吐量：**24,017 samples/s** vs ~100/s

4. **早期检测**：50包足够检测所有攻击类型

### 论文中的表述

- ❌ "我们的方法比参考论文更快"（在单流场景下他们50包确实更快）
